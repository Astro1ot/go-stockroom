# Что уметь объяснить на собеседовании

Начните с реального сценария: «Два покупателя одновременно заказывают последнюю клавиатуру. Один заказ должен пройти, второй получить 409, остаток — остаться нулевым».

1. **Почему обычных SELECT и UPDATE недостаточно?** Между чтением остатка и записью другой запрос может изменить данные. Блокировка строки удерживается до завершения транзакции и связывает проверку со списанием.
2. **Что означает атомарность здесь?** Заказ, его позиции и все изменения остатков фиксируются вместе. Нехватка второго товара отменяет уже сделанное списание первого.
3. **Почему сортируются ID товаров?** Разный порядок получения нескольких блокировок создаёт условия для deadlock. Создание и отмена используют одинаковый порядок. Это снижает риск в этих операциях; новые операции тоже должны соблюдать порядок.
4. **Как защищён повтор POST?** Уникальный ключ в БД плюс хеш нормализованного запроса. Уникальное ограничение работает и между разными экземплярами API.
5. **Почему не хранить ключ только в Redis?** Заказ и запись ключа должны быть атомарными. Отдельная запись в Redis усложняет согласованность двух хранилищ.
6. **Зачем сохранять цену в order_items?** Цена товара может измениться, а старый заказ должен сохранить исходную стоимость.
7. **Почему деньги не float64?** Целые копейки позволяют избежать ошибок двоичного представления десятичных дробей. Мультивалютность и дробные количества в проект не входят.
8. **Какие JOIN применены?** orders → order_items → products. Запрос получает позиции и названия товара одним обращением к БД.
9. **Почему PostgreSQL может не использовать индекс?** Для маленькой таблицы последовательное чтение дешевле. Это проверяется EXPLAIN на представительных данных, а не предположением «индекс всегда быстрее».
10. **Что будет без Redis?** Каталог читается из БД. Складские операции от Redis не зависят. Есть короткие таймауты кеша, чтобы ошибка кеша не задерживала весь запрос надолго.
11. **Какие принципы проектирования видны?** Ответственность HTTP, предметных правил и SQL разделена. Сервис зависит от интерфейса Store. В Go используются интерфейсы и композиция вместо иерархии классов.
12. **Сложность нормализации заказа?** Агрегация через map — в среднем O(n), сортировка k уникальных товаров — O(k log k), дополнительная память O(k).

## Самостоятельные упражнения

- Пройдите путь одного POST от роутера до COMMIT и объясните каждую проверку.
- Запустите `TestIntegrationConcurrentLastItem`, затем временно уберите блокировку в отдельной ветке и исследуйте последствия.
- Добавьте фильтр списка заказов по клиенту и пагинацию. Сравните EXPLAIN до и после индекса на достаточно большой учебной выборке.
- Добавьте состояние «оплачен» и запрет его отмены. Сначала сформулируйте правила, затем измените схему, сервис и тесты.
